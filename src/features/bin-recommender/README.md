# bin-recommender

Static lookup table that predicts a bin's `WxDxH` size from its user-entered label, trained from production ML telemetry. Powers the inline size suggestion under the label field in the bin inspector.

## UI

`useBinSizeSuggestion(label, drawer, current)` fetches `model.json` via `loadModel.ts` and returns a prediction — suppressing the drawer-prior tier (dominated by the trivial `1x1x3` default) so only label/embed matches surface. The `BinSizeSuggestion` component renders the passive hint; the bin-inspector lazy-loads it and supplies `canFit` (via `canPlaceBin`) so the one-tap **Apply** shows only when the suggested size fits — otherwise the row stays informational ("Won't fit here").

## Contract

```ts
import { recommendBinSize } from '@/features/bin-recommender';
import model from '@/features/bin-recommender/model.json';

const prediction = recommendBinSize({
  label: 'screws',
  drawer: { width: 8, depth: 12, height: 4 },
  model,
});
// prediction: { size: { width, depth, height }, p: 0.62, n: 41, source: 'label' } | null
```

The consumer is responsible for loading `model.json` — `useBinSizeSuggestion` calls `loadBinRecommenderModel()` so the asset is only fetched when the Labs flag is on.

The function returns `null` whenever:

- The model's `schemaVersion` doesn't match the runtime (forward-incompat artifact)
- The model's `vocabVersion` doesn't match `VOCAB_VERSION` from the telemetry module (model was trained against a different vocab — short-circuits one-shot with a warning)
- The label is blank or whitespace AND there's no drawer-prior with enough support
- Every source in the resolution cascade has fewer than its minimum-sample threshold

## Resolution cascade

| Tier       | Source                  | Threshold | Used when                                                                                                      |
| ---------- | ----------------------- | --------- | -------------------------------------------------------------------------------------------------------------- |
| PRIMARY    | `byLabelHash[hash]`     | `n ≥ 10`  | Label hashes match exactly. Handles any language because the hash is computed on `label.toLowerCase().trim()`. |
| ENRICHMENT | `byEmbedBucket[bucket]` | `n ≥ 20`  | OOV labels. Same 4-char semantic bucket the telemetry already records — covers synonyms and minor typos.       |
| FALLBACK   | `byDrawer["WxDxH"]`     | `n ≥ 50`  | Nothing else hits. Drawer-size prior — what people put in drawers of this size, regardless of label.           |

`pickTop()` returns the top-ranked size only (the JSON keeps top-3 for future tie-breaking but the runtime currently uses just the top entry).

## Training

The model artifact (`model.json`) is regenerated by `scripts/train-bin-recommender/train.py`. See that directory's README for the workflow. The committed artifact carries trained data; if it is ever emptied, `recommendBinSize` returns `null` on every call until the next training run.

## Why client-side?

- **Zero API cost.** The recommender ran ~250k inferences during local QA testing; doing that against a serverless endpoint would crush the Redis command budget.
- **Offline-safe.** PWA users (the app's primary deployment surface) keep working without a network.
- **Privacy-clean.** No label text leaves the device for the suggestion path — the hash is computed client-side and matched against pre-computed buckets.

## Bundle impact

`loadModel.ts` imports the file with `?url` — Vite still resolves and content-hashes it at build time, so a rename is a build error rather than a production 404 — and fetches it only when a suggestion is actually requested.

The weights are therefore an **asset, not a JS chunk**: they sit under the `Fetched JSON assets (gzip)` size budget instead of the app-JS one, and the service worker runtime-caches them on first use rather than precaching them. Keep the committed JSON pretty-printed so retrain diffs stay reviewable — `scripts/vite-plugin-minify-json-assets.ts` compacts it on emit.
